## 一、公共文件清单与修改权限

公共文件指**多人可能同时修改**的文件，修改前必须确认权限。

| 文件 | 作用 | 修改权限 | 说明 |

| `backend/.prettierrc` | 格式化规则 | ⚠️ 需通知全组 | 代码格式变更 |
| `backend/.gitignore` | Git 忽略 | ✅ 可自行修改 | 新增忽略规则不影响他人 |
| `backend/src/app.ts` | 应用入口/路由挂载 | 🚫 仅组长可改 | 路由统一由组长挂载，组员提 PR |

## 二、依赖版本管理规范

### 2.1 版本号规则

所有依赖使用 **`^` 前缀**（允许小版本升级），但**核心框架锁定大版本**：

```json
"vue": "^3.5.42",        // ✅ 允许 3.x 升级，不允许 4.x
"express": "^5.1.0",     // ✅ 允许 5.x 升级
"typescript": "~6.0.2"   // ⚠️ 特殊：TS 用 ~ 只允许补丁升级
```

### 2.2 当前锁定的核心版本（不得随意升级大版本）

#### 后端

| 依赖 | 锁定版本 | 说明 |
|------|---------|------|
| Node.js | >= 18 | 运行环境 |
| express | ^5.x | Web 框架 |
| better-sqlite3 | ^13.x | SQLite 驱动 |
| typescript | ^5.x | TS 编译器 |
| vitest | ^5.x | 测试框架 |

#### 前端

| 依赖 | 锁定版本 | 说明 |
|------|---------|------|
| vue | ^3.x | 前端框架（禁止升级到 Vue 4） |
| vue-router | ^4.x | 路由 |
| echarts | ^6.x | 图表库 |
| vite | ^8.x | 构建工具 |
| typescript | ~6.0.x | TS 编译器（只允许补丁升级） |

### 2.3 新增依赖流程

1. **先在群里说明**：需要装什么包、用来做什么
2. **安装**：`npm install <包名>`（会自动更新 package.json 和 lock 文件）
3. **提交**：把 `package.json` 和 `package-lock.json` 一起提交
4. **通知组员**：让他们拉取后执行 `npm install`

### 2.4 禁止事项

- ❌ 禁止手动编辑 `package-lock.json`
- ❌ 禁止删除 `package-lock.json` 后重新生成（会导致版本漂移）
- ❌ 禁止未经同意升级核心框架大版本（如 Vue 3 → 4）
- ❌ 禁止使用 `npm install <包>@latest`（用具体版本号）

## 三、配置文件修改规范

### 3.1 后端端口与地址

- 后端端口：**3000**（已在 `config.ts` 中配置，8000 被系统占用）
- 前端地址：`http://localhost:5173`
- CORS 已配置允许该地址跨域

如需修改端口，必须：
1. 修改 `backend/.env`（不提交）或 `backend/src/config.ts` 的默认值
2. 同步修改 `frontend/src/api/*.ts` 中的 BASE_URL
3. 通知全组

### 3.2 环境变量

- `.env` 文件**禁止提交到 Git**（已在 `.gitignore` 中）
- 如需新增环境变量，在 `.env.example` 中添加模板并提交
- 组员根据 `.env.example` 自行创建 `.env`

### 3.3 TypeScript 配置

- `strict: true` 严格模式，**不得关闭**
- 如需修改 `tsconfig.json`，必须在群里说明原因

## 四、Git 分支与合并流程

### 4.1 分支策略

```
main (主分支，全组共享，始终可运行)
  │
  ├── feature/analytics    (成员 D：数据大屏)
  ├── feature/chat         (成员 B：问答对话)
  ├── feature/xxx          (其他成员各自的功能分支)
```

### 4.2 开发流程

1. **从 main 拉取最新**：`git checkout main && git pull`
2. **创建功能分支**：`git checkout -b feature/你的模块名`
3. **在功能分支上开发**，提交自己的代码
4. **推送到远程**：`git push -u origin feature/你的模块名`
5. **开发完成后**，在 GitHub 上发起 Pull Request 合并到 main
6. **组长审核**后合并

### 4.3 提交信息规范

格式：`<类型>(<模块>): <描述>`

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(analytics): 新增情感分析接口` |
| `fix` | 修复 Bug | `fix(chat): 修复流式响应中断问题` |
| `refactor` | 重构 | `refactor: 统一日志模块` |
| `docs` | 文档 | `docs: 更新协作规范` |
| `test` | 测试 | `test(analytics): 补全单元测试` |
| `chore` | 构建/工具 | `chore: 配置 ESLint` |

## 五、冲突解决规范

### 5.1 拉取前准备

每次拉取远程代码前，先提交或暂存本地修改：

```bash
# 方案 A：暂存本地修改
git stash
git pull
git stash pop

# 方案 B：先提交本地修改
git add .
git commit -m "wip: 临时提交"
git pull
```

### 5.2 解决冲突步骤

1. 执行 `git pull` 后如果提示冲突，运行 `git status` 查看冲突文件
2. 打开冲突文件，找到以下标记：

```
<<<<<<< HEAD
  （你本地的代码）
=======
  （远程拉取的代码）
>>>>>>> origin/main
```

3. **手动合并**：保留两边需要的代码，删除三行标记
4. 标记已解决：`git add <文件名>`
5. 完成合并：`git commit`

### 5.3 常见冲突处理

#### app.ts 路由冲突

两边的 import 和路由挂载都保留：

```typescript
import chatRouter from './routes/chat.js';
import analyticsRouter from './analytics/routes.js';
import yourRouter from './routes/your.js';

app.use('/api/v1/chat', chatRouter);
app.use('/api/v1/analytics', analyticsRouter);
app.use('/api/v1/your', yourRouter);
```

#### main.ts 插件冲突

两边的插件都保留，按顺序 use：

```typescript
import { createPinia } from 'pinia';
import router from './router';

const app = createApp(App);
app.use(createPinia());
app.use(router);
app.mount('#app');
```

#### package.json 依赖冲突

1. 手动合并 `dependencies` 和 `devDependencies` 对象
2. **删除 `package-lock.json`**
3. 重新执行 `npm install` 生成新的 lock 文件
4. 提交 `package.json` 和新的 `package-lock.json`

### 5.4 冲突解决后验证

```bash
# 后端
cd backend
npm install
npm run build    # 确认能编译通过

# 前端
cd frontend
npm install
npm run build    # 确认能编译通过
```

验证通过后再提交，避免把编译错误合并到 main。

1. **不要直接在 main 分支上开发**，必须用 feature 分支
2. **每次开始工作前先 `git pull`**，保持本地最新
3. **提交前先 `npm run build`**，确保代码能编译
4. **大文件（图片、模型）不要提交到 Git**，用其他方式共享
5. **有疑问先在群里问**，不要擅自修改公共文件
