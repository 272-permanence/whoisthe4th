PART 2 · TRACE ID

全链路追踪：从前端点击到后端落库

前端 → 后端

// apiClient 自动注入 async function apiFetch(path, opts) { const headers = { 'X-Trace-Id': getTraceId(), // localStorage 有则复用 'Authorization': 'Bearer ' + token } const res = await fetch(fullUrl, { headers }) // 响应头回写 → 下次请求继续用同一个 res.headers.get('X-Trace-Id') && localStorage.setItem('traceId', traceId) }

后端存储

const traceStorage = new AsyncLocalStorage() function traceIdMiddleware(req, res, next) { const traceId = req.headers['x-trace-id'] ?? crypto.randomUUID() req.traceId = traceId res.setHeader('X-Trace-Id', traceId) traceStorage.run({ traceId }, () => next()) }

安全设计（D 补充）

function normalizeTraceId(raw) { // 只允许字母数字和 .-_ ，防日志注入 return /^[A-Za-z0-9._-]+$/.test(raw) && raw.length <= 64 ? raw : null }

PART 3 · MASKING

脱敏：敏感字段绝对不能明文落库

B 的 mask.ts

const SENSITIVE_KEYS = [ 'password', 'token', 'mobile', 'phone', 'card', 'secret', 'authorization', 'cookie', 'apikey', 'openid' // ... 30+ 关键词 ] export function maskParams(obj) { return recurse(obj, false) // 递归脱敏 } export function maskMobile(phone) { return phone.replace(/(\d{3})\d{4}(\d{4})/, '$1****$2') } // 13812345678 → 138****5678

✅ 实测效果（后端日志）

请求参数：
{
username: "admin",
password: "***", ← 已脱敏
mobile: "138****5678", ← 已脱敏
headers: {
Authorization: "****"
}
}
⚠️ 硬约束
脱敏后不可逆！永远不写反向还原函数。密码在落库前已经是 `***`，审计员也看不到原始内容。
讲脱敏策略，强调不可逆约束
PART 4 · REDIS STREAM

为什么用 Redis Stream 解耦日志写入？

⚡ 核心收益
业务接口不等日志落库就返回。MySQL 慢 / 挂了不影响用户体验，最多日志丢在队列里。
🔄 降级策略
Redis 不可用时 enqueueLog() 返回 false，dispatch() 自动走 persistLog() 直写 MySQL。
🔒 消费者组
XREADGROUP 保证消息至少被消费一次。落库失败不 ACK，消息留在 pending 队列等人工处理。

D 的 logService.dispatch() 核心代码

async function dispatch(type, entry) { try { if (await enqueueLog(type, entry)) return // ✅ Redis 可用 await persistLog(type, entry) // ⬇️ 降级直写 } catch (error) { log.ERROR(`保存${type}日志失败: ${error}`) // 💡 吞异常，不阻塞业务 } }
讲 Redis Stream 设计 + 降级策略 + 为什么不阻塞

DEMO · 04（可选）

Redis Stream pending 机制：落库失败不 ACK，消息留在队列等重试

redis-cli
$ redis-cli XLEN scenic:log:stream
(integer) 0

$ redis-cli XINFO CONSUMER scenic:log:stream log-writer node-12345
pending: 0

# 故意让 MySQL 挂掉（比如 TRUNCATE 后立即停 mysqld）
# 再 seed 一批
$ node scripts/seed-log-demo.mjs
后端 WARN: MySQL 不可用，但 Redis Stream 生产者 XADD 已入队

$ redis-cli XINFO CONSUMER scenic:log:stream log-writer node-12345
pending: 30 ← 消息留在这里，没有被 ACK！

# MySQL 恢复后，重启后端或手动 XCLAIM
# pending 会被下一次消费自动 ACK
🎯 讲解点
logQueue.ts 写死的策略：落库失败绝不 XACK。

正常消费完 → MySQL INSERT 成功 → XACK → 消息从队列移除。落库失败 → 不 ACK → 消息留在 pending 列表 → 下次消费循环自动重试。

这就是"异步不等于丢"。老师问"消息队列可靠吗"——这个 pending 机制就是我们的答案。
⏱ 时间不够就跳过这张，前三张覆盖已足够
Demo 第 4 段：可选，用 redis-cli 看 XLEN/XINFO CONSUMER

🎯 讲解点

DEMO · 07

reset → seed → 三条查询接口 → 三表 total 全部实时反映

Terminal
# 完整跑完 seed（不 step），等 2 秒 Redis Stream 消费完
[summary] operation=total_20 error=total_12 login=total_5

# 用 PowerShell 一口气查三个
$h = @{Authorization='Bearer 1:admin:admin';'x-user-role'='admin'}
Invoke-RestMethod 'http://localhost:8000/api/v1/logs/operation?pageSize=1' -Headers $h
→ data.total = 20
Invoke-RestMethod 'http://localhost:8000/api/v1/logs/error?pageSize=1' -Headers $h
→ data.total = 12
Invoke-RestMethod 'http://localhost:8000/api/v1/logs/login?pageSize=1' -Headers $h
→ data.total = 5

# 再查那条全链路 traceId
Invoke-RestMethod 'http://localhost:8000/api/v1/logs/trace/demo-chain-xxx' -Headers $h
→ operationCount=1 errorCount=1 ✅ 两表都命中
🎯 讲解点
reset → seed → 查询，这个闭环就是我们 20 分钟分享的主线。

老师可以现场看到：reset 前 total 可能是几十上百，reset 后立刻变 0，seed 跑完立刻变成我们造的数。没有"等一会儿"、没有清缓存、没有重启服务——这就是 Redis Stream 异步消费的实时性。

三表数量：operation 20 = 3 中间件 + 16 埋点 + 1 chain；error 12 = 6 前端 JS + 4 登录失败 + 1 非法 JSON + 1 chain；login 5 = 1 成功 + 4 失败。每个数都有来源，经得起追问。

踩坑总结 & Takeaways
进入总结
LESSONS LEARNED

合并过程中我们踩了这些坑

🔁 三方各写 traceId middleware
最终合并：C 的 AsyncLocalStorage + D 的安全校验 + B 的 logger 集成。不能各自为战，统一规范！
⚠️ 同时 declare Express.Request.user
C 的 middleware/auth.ts 和 D 的 authGuard.ts 同时声明但类型不同 → tsc 报错。全局类型声明只能一处！
🔧 MySQL 端口假设错误
B 假设 3307，本地实际跑在 3306。改 .env 后 tsx watch 不会重读 .env，需彻底重启。端口别硬编码，config 里统一读。
🏷️ ESM import 必须带 .js
TypeScript 源码里 `import { x } from './foo.js'` 不是 `'./foo'`。tsx 虽然宽松但 ESM 规范必须遵守。
分享踩坑经验，让同学避开相同问题
KEY TAKEAWAYS

核心收获（请记住这 4 点）

1
日志即财富
没有日志的线上 = 盲人摸象。哪怕 console.log 也比没日志强。
2
链路追踪先行
traceId 从前端埋 → 后端传 → 数据库查，一次请求一次 ID 串联到底。
3
脱敏不可逆
敏感字段落库前必须 mask，并且永远不写还原函数。这是硬约束。
4
降级兜底
Redis 挂了降级 MySQL，MySQL 挂了降级 Pino 文件。多层兜底 = 永不丢日志。
