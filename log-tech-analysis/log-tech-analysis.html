PART 1 · LOGGER

日志框架选型：为什么选 Pino？

框架底层JSON 结构化异步写入性能（ops/s）学习成本
WinstonNode 原生✅ 需配置⚠️ 同步默认~20K低
BunyanNode 原生✅ 原生⚠️ 部分同步~50K中
PinoC++ 底层✅ 原生✅ libuv 异步~300K低
MorganExpress 中间件❌ 纯文本❌ 同步~10K极低
✅ Pino 优势
C++ + libuv 异步、单文件零配置、pino-pretty 开发态、child() 上下文注入、生态成熟（pino-syslog、pino-datadog）
⚙️ 我们的配置
开发态 → pino-pretty 彩色控制台；生产态 → JSON 文件 `app.log`，`sync: false` 异步写入；traceId 通过 AsyncLocalStorage 自动注入

PART 2 · TRACE ID

全链路追踪：从前端点击到后端落库

前端 → 后端

// apiClient 自动注入 async function apiFetch(path, opts) { const headers = { 'X-Trace-Id': getTraceId(), // localStorage 有则复用 'Authorization': 'Bearer ' + token } const res = await fetch(fullUrl, { headers }) // 响应头回写 → 下次请求继续用同一个 res.headers.get('X-Trace-Id') && localStorage.setItem('traceId', traceId) }

后端存储

const traceStorage = new AsyncLocalStorage() function traceIdMiddleware(req, res, next) { const traceId = req.headers['x-trace-id'] ?? crypto.randomUUID() req.traceId = traceId res.setHeader('X-Trace-Id', traceId) traceStorage.run({ traceId }, () => next()) }

安全设计（D 补充）

function normalizeTraceId(raw) { // 只允许字母数字和 .-_ ，防日志注入 return /^[A-Za-z0-9._-]+$/.test(raw) && raw.length <= 64 ? raw : null }

PART 3 · MASKING

脱敏：敏感字段绝对不能明文落库

B 的 mask.ts

const SENSITIVE_KEYS = [ 'password', 'token', 'mobile', 'phone', 'card', 'secret', 'authorization', 'cookie', 'apikey', 'openid' // ... 30+ 关键词 ] export function maskParams(obj) { return recurse(obj, false) // 递归脱敏 } export function maskMobile(phone) { return phone.replace(/(\d{3})\d{4}(\d{4})/, '$1****$2') } // 13812345678 → 138****5678

✅ 实测效果（后端日志）

请求参数：
{
username: "admin",
password: "***", ← 已脱敏
mobile: "138****5678", ← 已脱敏
headers: {
Authorization: "****"
}
}
⚠️ 硬约束
脱敏后不可逆！永远不写反向还原函数。密码在落库前已经是 `***`，审计员也看不到原始内容。
讲脱敏策略，强调不可逆约束
PART 4 · REDIS STREAM

为什么用 Redis Stream 解耦日志写入？

⚡ 核心收益
业务接口不等日志落库就返回。MySQL 慢 / 挂了不影响用户体验，最多日志丢在队列里。
🔄 降级策略
Redis 不可用时 enqueueLog() 返回 false，dispatch() 自动走 persistLog() 直写 MySQL。
🔒 消费者组
XREADGROUP 保证消息至少被消费一次。落库失败不 ACK，消息留在 pending 队列等人工处理。

D 的 logService.dispatch() 核心代码

async function dispatch(type, entry) { try { if (await enqueueLog(type, entry)) return // ✅ Redis 可用 await persistLog(type, entry) // ⬇️ 降级直写 } catch (error) { log.ERROR(`保存${type}日志失败: ${error}`) // 💡 吞异常，不阻塞业务 } }
讲 Redis Stream 设计 + 降级策略 + 为什么不阻塞

CHAPTER 05
踩坑总结 & Takeaways
进入总结
LESSONS LEARNED

合并过程中我们踩了这些坑

🔁 三方各写 traceId middleware
最终合并：C 的 AsyncLocalStorage + D 的安全校验 + B 的 logger 集成。不能各自为战，统一规范！
⚠️ 同时 declare Express.Request.user
C 的 middleware/auth.ts 和 D 的 authGuard.ts 同时声明但类型不同 → tsc 报错。全局类型声明只能一处！
🔧 MySQL 端口假设错误
B 假设 3307，本地实际跑在 3306。改 .env 后 tsx watch 不会重读 .env，需彻底重启。端口别硬编码，config 里统一读。
🏷️ ESM import 必须带 .js
TypeScript 源码里 `import { x } from './foo.js'` 不是 `'./foo'`。tsx 虽然宽松但 ESM 规范必须遵守。
分享踩坑经验，让同学避开相同问题
KEY TAKEAWAYS

核心收获（请记住这 4 点）

1
日志即财富
没有日志的线上 = 盲人摸象。哪怕 console.log 也比没日志强。
2
链路追踪先行
traceId 从前端埋 → 后端传 → 数据库查，一次请求一次 ID 串联到底。
3
脱敏不可逆
敏感字段落库前必须 mask，并且永远不写还原函数。这是硬约束。
4
降级兜底
Redis 挂了降级 MySQL，MySQL 挂了降级 Pino 文件。多层兜底 = 永不丢日志。
最后总结四个核心 Takeaways
