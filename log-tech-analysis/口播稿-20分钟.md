### 4:20 – 5:30 ｜ 日志框架对比 + Pino 原理（题目要求必讲）

【画面】「日志框架对比与 Pino 原理」

【口播】
"进入核心技术，第一件事是选框架。

日志框架主流有五个：Winston、Bunyan、Pino、log4js、Morgan。

Winston 生态最全，但默认同步写，吞吐只有两万左右；Bunyan 原生 JSON，但已经停止维护；log4js 是 Java 风格，配置重；Morgan 只能记 HTTP，纯文本，没法检索。

Pino 的吞吐是三十万每秒，比 Winston 高一个数量级。我们选它。

为什么这么快？三个原因。

第一，序列化在 C++ 层做。底层 sonic-boom 直接拼 JSON 字符串，不构造 JS 对象，也不走 `JSON.stringify` —— 少了两层开销。

第二，写入走 libuv 线程池。落盘是异步的，主线程只往缓冲区塞数据就返回。这一条对我们最关键，日志不能拖慢业务接口。

第三，`child()` 可以绑定上下文。每个请求派生一个 child logger，把 traceId、userId 绑进去，后面每行日志自动带上，不用手动传。

配置上我们做了两态：开发用 pino-pretty 彩色输出，生产写 JSON 到 `app.log`，并且 `sync: false` 异步写。

所以链路上是三层：Redis 队列 → MySQL → Pino 文件。前两层挂了，日志还在文件里。"

【过渡】
"框架选完，接下来三个概念，讲完就直接演示。"

二是刚才提到的 `req.path` 被改写的问题。日志模块最容易出的 bug，就是你以为记的是真实值，其实已经被框架改过了。

这两条，建议做类似功能的同学提前避一下。"

## 五、老师可能追问的问题

**Q：为什么要自建，不用 ELK / Sentry？**
A：课程项目规模小，引入 ELK 要额外部署三四个服务。我们选择 MySQL + Redis，都是项目已有的依赖，零新增运维成本。但架构上留了扩展空间 —— `dispatch()` 是个统一入口，以后要接 Sentry，改一处就行。

**Q：日志量大了 MySQL 撑得住吗？**
A：撑不住，这是明确的局限。真到百万级日活，应该改成 ES 或者 ClickHouse。但我们现在做了两件事控量：一是中间件跳过静态资源和健康检查，二是三张表都有时间索引，支持按时间范围查询。目前的数据量是完全够用的。

**Q：脱敏之后怎么排查具体用户的问题？**
A：靠 traceId，不靠用户名。用户报错的时候我们拿到的是 traceId，能定位到具体哪次请求、什么参数、什么堆栈。至于"这个用户是谁"，如果需要精确定位，走后台的审计接口，那里有权限校验，不需要在日志里存明文。

**Q：异步写日志，服务一崩，队列里的日志是不是就丢了？**
A：Redis Stream 是持久化的，服务崩了消息还在 Redis 里，重启后消费组会接着消费。而且我们还有 Pino 文件兜底 —— 写队列的同时，文件日志也写了一遍。

**Q：为什么前端也要埋点，后端记接口不够吗？**
A：不够。后端只知道自己收到了什么请求，不知道用户在页面上点了什么、在哪停留。比如"用户看了景点列表但没点详情"这种流失，后端日志里是空白的，只有前端埋点能看到。

## 六、现场事故预案

| 情况 | 处理 |
|---|---|
| 后端 8000 挂了 | 切到 backend 终端，`node node_modules/tsx/dist/cli.mjs src/app.ts`，等 5 秒 |
| MySQL 连不上 | `Get-NetTCPConnection -LocalPort 3307`，没有就说明 mysqld 停了，需要重启 phpstudy 里的 MySQL 8.0 |
| Redis 报 NOGROUP | `node scripts/reset-logs.mjs` 会重建消费组定位点，跑一次即可 |
| reset 后消费者报错刷屏 | 不用管，reset 脚本已经用 XTRIM 保住了 Stream，不会再报 |
| 查出来数字不对 | 别解释，直接说"我重跑一次 reset 和 seed"，然后重跑。数字对不上比慢了更致命 |
| 投影看不清 | 浏览器按 F 全屏；字号是按 1920×1080 设计的，全屏下最小字号约 18px |
